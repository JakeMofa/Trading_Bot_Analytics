BTC INTELLIGENCE SYSTEM - COMPLETE ARCHITECTURE
===============================================

PURPOSE
-------

Build a local-first real-time Bitcoin intelligence and prediction system focused first on
Polymarket US "BTC Up or Down - 15 Minute" markets.

The system's primary question is:

    What is the probability that the final Polymarket settlement value will be
    greater than or equal to the current "Price to Beat" at the end of the
    active 15-minute interval?

Primary output:

    P(UP)
    P(DOWN)
    Confidence
    Main reasons
    Contradictions / risks
    Comparison against Polymarket's own implied probability

The system should not claim certainty or 100% accuracy. It should behave as a continuously
running probability engine that measures and improves its own performance over time.


CORE DESIGN PRINCIPLE
---------------------

The system has four major responsibilities:

1. PYTHON / DETERMINISTIC CALCULATIONS
   - collect data
   - maintain current state
   - calculate features
   - manage sessions
   - store history
   - perform exact math

2. MACHINE LEARNING
   - learn statistical patterns
   - estimate probabilities
   - compare current states to historical states
   - combine multiple signals

3. OPENAI
   - interpret news and unusual events
   - reason over contradictions
   - inspect compact structured state
   - act as a higher-level analyst
   - NOT process every raw tick
   - NOT be the primary mathematical prediction engine

4. SQLITE MEMORY
   - store markets
   - store snapshots
   - store features
   - store predictions
   - store outcomes
   - store events/news
   - store relationship edges
   - support FTS5 text search
   - later support semantic/vector retrieval if needed

POLYMARKET SESSION BEHAVIOR
---------------------------

The system must never rely on one hard-coded Polymarket URL.

A URL such as:

    btc-updown-15m-2026-09-29-2315z

represents one specific 15-minute market.

Every 15 minutes:

    - the current market expires
    - a new market becomes live
    - the Price to Beat changes
    - the timer resets
    - the Polymarket odds reset to the new market
    - the system must automatically follow the newest active interval

This must simulate the user pressing "Go to live" automatically.

SESSION START LOGIC
-------------------

When the application starts:

    1. determine the current UTC time
    2. discover the currently active Polymarket BTC 15-minute market
    3. retrieve:
       - market ID
       - market slug / URL if useful
       - start time
       - end time
       - Price to Beat
       - current Up price
       - current Down price
       - market status
    4. calculate:
       - elapsed seconds
       - remaining seconds
    5. backfill recent BTC data
    6. connect live WebSockets
    7. begin prediction immediately
    8. mark whether we joined the interval late

The application must work even if it starts with:

    10 minutes remaining
    5 minutes remaining
    2 minutes remaining
    30 seconds remaining

If the app starts late in a session, it should still backfill recent prices/trades where possible.

Example:

    Market:
        6:15 PM -> 6:30 PM

    App starts:
        6:21 PM

    System should:
        - discover the live market
        - obtain Price to Beat
        - know 6 minutes already elapsed
        - know 9 minutes remain
        - backfill market history from exchange APIs
        - begin live monitoring immediately

At the next boundary, the system will have full capture from second zero.


GO-TO-LIVE ROLLOVER LOGIC
-------------------------

At market expiration:

    1. save final prediction state
    2. retrieve final market outcome
    3. save:
       - final price
       - final result: UP or DOWN
       - whether predictions were correct
    4. discover the next live BTC 15-minute market
    5. capture its new Price to Beat
    6. reset live interval state
    7. continue without restarting the application

The system should run indefinitely.

CALCULATION LAYER
-----------------

This layer is pure Python / numerical code.

It should calculate exact values and features without using OpenAI.

Core calculations:

1. TARGET/TIME
    distance_to_target =
        current_btc_price - price_to_beat

    distance_to_target_percent =
        distance_to_target / price_to_beat

    seconds_remaining =
        market_end - current_time

2. MOMENTUM
    returns / price changes over:
        5 sec
        10 sec
        30 sec
        1 min
        5 min
        15 min
        1 hour
        4 hours
        24 hours

3. VOLATILITY
    rolling realized volatility over:
        30 sec
        1 min
        5 min
        15 min
        1 hour

4. ORDER FLOW
    market buy volume
    market sell volume
    aggressive buy/sell imbalance
    volume delta
    trade velocity
    volume acceleration

5. ORDER BOOK
    bid/ask depth
    bid/ask imbalance
    spread
    microprice
    liquidity near current price
    liquidity near Price to Beat
    depth changes
    large liquidity walls

6. DERIVATIVES
    funding rate
    funding z-score later
    open interest
    open interest change
    liquidation pressure
    long/short liquidation imbalance
    perpetual basis later

7. POLYMARKET
    current Up price
    current Down price
    implied market probability
    probability change over time
    odds velocity
    difference between our prediction and market pricing

HISTORICAL MODEL
----------------

The historical model is the system's quantitative memory.

It asks:

    "Have we seen similar conditions before, and what happened?"

Example current state:

    BTC = $38 below Price to Beat
    5 minutes 10 seconds remaining
    order flow strongly bearish
    volatility high
    open interest falling

The historical model can search past states with similar:

    distance to target
    time remaining
    momentum
    volatility
    order flow
    order-book imbalance
    open-interest behavior
    liquidation environment
    Polymarket odds
    market regime

It can produce something like:

    similar cases found: 214
    ended DOWN: 148
    ended UP: 66

    historical tendency:
        DOWN 69%
        UP 31%

This becomes one input into the meta-model.

Initially, similarity can be simple:
    - nearest neighbors
    - standardized feature distance
    - regime filters
    - XGBoost / LightGBM history model

No advanced vector database is required at first.

META-MODEL / FINAL BRAIN
------------------------

The meta-model combines all specialist model outputs and important raw features.

Example:

    Target/time model      DOWN 66%
    Order flow model       DOWN 72%
    Order book model       DOWN 64%
    Derivatives model      DOWN 59%
    Historical model       DOWN 69%
    AI/news model          NEUTRAL
    Polymarket crowd       DOWN 63%

The meta-model should NOT just average these percentages.

It should learn context-dependent weights.

Examples:

    High volatility:
        trust order flow and derivatives more

    Quiet market:
        trust order book and target/time more

    Major macro event:
        increase AI/news and macro weight

    Final 60 seconds:
        target/time mathematics becomes much more important

Final result example:

    UP    30%
    DOWN  70%
    Confidence 76%


OPENAI ROLE
-----------

OpenAI should NOT:

    - receive every raw BTC tick
    - receive every order-book update
    - calculate simple math
    - calculate volatility
    - replace the numerical prediction model
    - be called every second

OpenAI SHOULD:

    - understand news
    - interpret macro events
    - interpret regulatory events
    - summarize unusual market conditions
    - inspect contradictions between models
    - provide a compact reasoning layer
    - classify event relevance to BTC
    - identify risks the numerical model may be missing

Python compresses the live market into a small structured payload.

Example:

    {
      "distance_to_target": -37.22,
      "seconds_remaining": 310,
      "momentum_1m": -0.12,
      "momentum_5m": -0.31,
      "order_flow": -0.63,
      "book_imbalance": -0.28,
      "volatility": 0.19,
      "oi_change": -0.42,
      "polymarket_up": 0.34
    }

OpenAI may also receive:
    - 3-10 relevant historical cases
    - one or two important recent events
    - specialist model outputs

OpenAI returns a short structured response.

Example:

    {
      "direction_bias": "down",
      "confidence": 0.71,
      "important_risk": "short liquidation reversal",
      "contradictions": [
        "one-hour trend remains positive"
      ]
    }

OpenAI should be called selectively.

Possible call triggers:

    - new Polymarket interval begins
    - significant news arrives
    - specialist models strongly disagree
    - unusual/anomalous market state
    - optional high-level review every few minutes

This keeps token usage low.


LOCAL LLAMA
-----------

Local Llama/Ollama can later be used as:

    - a free first-pass news classifier
    - a fallback
    - a local event summarizer

But for initial testing, OpenAI can be used with pay-as-you-go API credits to evaluate how much intelligence it actually adds.

The numerical prediction system must continue working even if OpenAI is unavailable.

FTS5 TEXT MEMORY
----------------

SQLite FTS5 should index:

    news
    event summaries
    AI explanations
    model notes
    prediction explanations
    failure analysis

FTS5 is enough for V1.

No dedicated vector database is needed initially.


TRAVERSAL MEMORY
----------------

Use the relationships table as a lightweight knowledge graph.

This supports questions such as:

    Which predictions were wrong during high volatility?

    Which news events were associated with incorrect predictions?

    Which model was strongest during the final two minutes?

    Which historical patterns repeatedly occurred before UP outcomes?

Recursive SQL can traverse relationships.

Later, if useful:
    migrate traversal data to PostgreSQL or Neo4j

But do not add those systems until needed.


VECTOR SEARCH
-------------

Do not add a vector DB in V1.

If FTS5 becomes insufficient and semantic similarity proves useful:

    Option A:
        store OpenAI embeddings locally

    Option B:
        migrate to PostgreSQL + pgvector

Potential uses:

    find semantically similar news events
    find similar AI explanations
    retrieve related market narratives

Numeric market-state similarity should still use numerical feature vectors, not text embeddings.

DATA RETENTION
--------------

Avoid storing every raw order-book update forever.

Suggested approach:

    raw order-book:
        short retention only if stored at all

    raw trades:
        limited retention

    derived features:
        keep long-term

    15-minute market records:
        keep indefinitely

    predictions:
        keep indefinitely

    outcomes:
        keep indefinitely

    important events/news:
        keep indefinitely

This is important because local disk space is limited.

The user's Mac had roughly 100 GB free when reviewed.

V1 should have a storage budget and automatic cleanup.

EVALUATION
----------

Never judge the model by a few successful predictions.

Track:

    directional accuracy
    Brier score
    log loss
    calibration
    confidence buckets
    accuracy by time remaining
    accuracy by market regime
    accuracy by volatility regime
    accuracy by model version

Compare against:

    50/50 baseline
    always-UP baseline
    always-DOWN baseline
    Polymarket implied probability
    simple target/time baseline

Example calibration analysis:

    predictions around 60%
        should be correct about 60% over time

    predictions around 80%
        should be correct about 80% over time

If the model says 80% but is only correct 55%, it is overconfident.


OPENAI EVALUATION
-----------------

We should measure whether OpenAI actually improves the model.

For every market, store:

    Quantitative model prediction
    OpenAI analyst opinion
    Combined prediction
    Polymarket probability
    Actual outcome

Then evaluate:

    Quant-only performance
    OpenAI-only performance
    Combined performance
    Polymarket performance

Possible result:

    OpenAI may help during news events
    OpenAI may hurt during quiet markets

The system should learn from evidence, not assume AI is always useful.

FINAL ARCHITECTURAL PHILOSOPHY
------------------------------

This is NOT:

    "Give GPT a BTC screenshot and ask Up or Down."

This IS:

    LIVE MARKET DATA
        +
    DETERMINISTIC CALCULATIONS
        +
    SHORT-TERM ROLLING HISTORY
        +
    STORED HISTORICAL MEMORY
        +
    MACHINE LEARNING
        +
    OPTIONAL OPENAI REASONING
        +
    META-MODEL
        +
    CONTINUOUS EVALUATION

The system should always be able to answer:

    What is the probability?
    Why?
    What information was used?

    What did Polymarket think?
    What happened afterward?
    Was the prediction correct?
    Was the confidence calibrated?

That is the intended architecture.
