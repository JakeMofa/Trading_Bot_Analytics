# I7 feature-cycle stall diagnosis and prepared fix

I7 remains OPEN. Production is still on a7c0989; this change is prepared and tested on the existing `codex/phase1-75-retention-enable` branch, without deployment or restart.

Production logs bracket one synchronous feature call from 2026-10-30 18:02:19.637356 UTC to 18:04:30.688175 UTC: 131.050819 seconds (13:02:19 to 13:04:30 America/Chicago). These are the adjacent pre/post-call log timestamps, not newly added per-query instrumentation. The earlier ~83-second estimate is no longer the current duration.

`rest_loop` invokes `capture_features` directly on the FastAPI/collector event loop. Its `features.calculate -> _price` SQL visits Coinbase stream rows using the `(source,event_id)` primary-key index, evaluates `julianday` on timestamps, and uses a temporary ORDER BY B-tree to choose one latest price. The received-at archive index does not satisfy this source-time ordering. Reference-price selection also scans/sorts. A native sample showed `sqlite3VdbeExec -> sqlite3_step`; syscall sampling showed thousands of pread64 calls against the database. All 15 samples in a 42-second stalled interval were in uninterruptible disk wait, not waiting for a SQLite writer lock: ~4.57% of one CPU, load ~1, 145 MiB API RSS, ~1.3 GiB available memory, 383,098,880 physical read bytes (~8.70 MiB/s). No waiting lock entries were observed. CPU-heavy Decimal work is not the evidenced cause. The exact SQL attribution combines call order, source, query plan and native I/O evidence; no invasive live SQL trace or individual full-query stopwatch was installed.

Bounded one-second HTTP probes timed out during the call; after completion they returned in ~14–109 ms. Coinbase, Polymarket and RAM state refreshed between cycles. Ensemble remained a separate responsive process: five-second scheduling, ~0.8-second computations after the delayed feature snapshot arrived. It repeatedly consumed the same stale snapshot while the next API feature cycle blocked. The serial REST supervisor starts the next cycle only after the previous call plus its pause; no overlapping feature jobs were observed. Lifecycle remained independently scheduled. This evidence supports synchronous SQLite page reads blocking the event loop, rather than a dead collector, scheduler overlap, subprocess wait or writer lock contention.

The smallest prepared containment fix runs the complete feature/forecast cycle through one awaited `asyncio.to_thread` call. Its connection is created and closed inside that worker; the event-loop collector connection is never shared across threads. Foreign keys stay enabled and the 5000 ms busy timeout is preserved. LiveState updates remain on the event loop, preserving existing market and freshness handling. Every cycle is awaited before the next starts; no detached periodic workers or second collector are created. Start/end/elapsed cycle logs make subsequent validation explicit.

This containment does **not** eliminate the expensive scan or prove production feature freshness. A cancelled await cannot forcibly interrupt an already running SQLite worker; it still closes its own connection on completion and cannot publish RAM results from the worker. Production-sized scan cost, WAL growth, writer coexistence and multiple live cycles must be verified before closing I7. Any later query/index optimization needs separate evidence of identical as-of/provenance/staleness behavior; no index or schema change is bundled here.

Validation: 182 backend tests and six deployment-control tests pass. Added regressions exercise a real collector save and RAM update while the worker holds a WAL read transaction, worker cleanup on failure, and identical feature values/quality/evidence with idempotent persisted forecasts. Existing timestamp/no-lookahead/stale-input tests remain unchanged.
