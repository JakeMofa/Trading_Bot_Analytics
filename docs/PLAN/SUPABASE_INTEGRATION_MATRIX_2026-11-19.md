# Supabase integrations for PP and production history

Reviewed November 19, 2026. This is documentation research, not hosted feature activation or release qualification. Browser observations are recorded separately. Current live forecasts stay in RAM and VM-local PostgreSQL; Supabase serves background persistence, explicit cold reads and research. PP and production retain distinct identities, origins, volumes and qualification gates.

## First implementation recommendation

Finish the existing exact structured cold-history reader and qualify a narrow read interface before adding another storage engine. The uncommitted `cold_structured_history.py` prototype already pages reviewed immutable revision IDs, validates receipt-bound envelope hashes and preserves exact decimal strings. Build on it. Its generated tests do not establish live permissions, discoverability, complete historical coverage or production support.

A useful next slice is a bounded historical query contract plus independently authenticated manifest/catalog discovery, a dedicated SELECT-only identity and an explicit cold endpoint. Keep import credentials out of the API. Return original revision bytes, origin/generation/market/time provenance, coverage and missing-history state. Test unavailable cloud, wrong origin, changed manifest, partial capture and concurrency before a release owner qualifies it on PP. A Data API adapter can serve this same contract after its separate permission and payload qualification; do not expose all of `history_v2` merely to make the API work.

## Capability matrix

“Use now” means reuse/qualify within the existing architecture, not a claim that a new hosted configuration is already authorized or enabled.

| Supabase capability | Useful PP/prod connection | Limits and required evidence | Disposition |
|---|---|---|---|
| Private PostgreSQL + client connection reuse | Existing VM outbox imports and exact receipt/revision reads; one bounded serial connection can avoid repeated setup | PR #155 measures receipt metadata only; #159 is default-off and generated full-path evidence. Keep separate transactions, deadlines, verified roles and ambiguous-commit recovery. Backend reuse is different from changing hosted pooler mode. [Connection guide](https://supabase.com/docs/guides/database/connecting-to-postgres) | Use existing path; measure before switching endpoints |
| Data API / REST | Backend HTTP access to selected historical manifests, immutable revisions and research summaries | Schema exposure, object grants and RLS are separate controls. The direct-SQL PP login's policies do not authorize an ordinary Auth JWT. Use an explicit API schema and narrow grants; preserve byte/string precision. [Data API security](https://supabase.com/docs/guides/api/securing-your-api) | Useful next adapter after contract qualification |
| Database functions / RPC | A bounded server-side historical query can combine joins and return one checked page with fewer round trips | Prefer `SECURITY INVOKER`; revoke default `PUBLIC` execution. Invoker alone does not make a function read-only. Enforce SELECT-only logic, caller scope, rows, bytes and deadline. [Functions](https://supabase.com/docs/guides/database/functions) | Strong candidate if measurements show query round trips matter |
| RLS / policies | Enforce PP versus prod origin and separate create-only archive writers from exact-key readers | An authenticated role is not sufficient authorization. Review all permissive/restrictive policies and privileged bypass paths. Policies do not make an archive immutable against owners. [Storage access](https://supabase.com/docs/guides/storage/security/access-control) | Essential existing boundary; qualify each new identity |
| Standard private Storage | Durable compressed raw chunks, exact manifests and explicit recovery downloads | Verify original bytes, digest, count and scope, not HTTP success alone. Database backup contains object metadata, not file bytes. [Private buckets](https://supabase.com/docs/guides/storage/buckets/fundamentals), [Backups](https://supabase.com/docs/guides/platform/backups) | Keep as raw archive tier; add independent recovery proof |
| S3-compatible Storage API | Existing tooling or independent backup/export client over the same stored objects | Generated S3 keys bypass RLS across buckets. JWT session-token access respects RLS; current docs require legacy anon key rather than publishable key for its secret parameter. This protocol does not add a second durable copy. [S3 auth](https://supabase.com/docs/guides/storage/s3/authentication) | Optional measured compatibility experiment; retain scoped HTTP reader |
| Edge Functions | Small authenticated archive-summary endpoints, cold-query façade or post-upload metadata checks near hosted services | Hosted limits: 256 MB memory, 2 seconds CPU/request, worker wall time 150 seconds free/400 seconds paid. Cloud code cannot reach VM-local partitions without a new network path. Never give an Edge request authority to retire local data. [Limits](https://supabase.com/docs/guides/functions/limits) | Later small orchestration task; compression/full replay stays on VM |
| Cron | Periodic hosted coverage summaries, overdue-upload checks and bounded reconciliation scheduling | Runs hosted SQL/functions or HTTP calls, not private VM scripts automatically. Docs recommend at most eight concurrent jobs and under ten minutes per job. [Cron](https://supabase.com/docs/guides/cron) | Useful after durable reconciliation contract exists |
| Queues / pgmq | Cloud-side retryable secondary jobs such as summaries or derived research exports | Visibility-window delivery guarantees are not end-to-end exactly-once side effects. Consumers still need idempotency, explicit completion and failure recovery. A cloud queue cannot persist a VM outbox item during a network outage. [Queues](https://supabase.com/docs/guides/queues) | Add only for independently justified cloud work |
| Database Webhooks / pg_net | Notify a summary worker that a cloud manifest or receipt batch changed | Asynchronous row-change HTTP notification is a hint, not exact archive proof. Persist job identity and recover missed work by query. Trigger definitions can expose embedded credentials in dumps; use reviewed secret storage. [Webhooks](https://supabase.com/docs/guides/database/webhooks) | Optional wake-up, never replacement for local outbox/ACK |
| Vault | Store cloud-side credentials used by approved SQL/Cron integrations | Secrets are encrypted at rest but available decrypted to authorized SQL. Restrict decrypted-view privileges. It does not distribute credentials to VMs automatically. [Vault](https://supabase.com/docs/guides/database/vault) | Use only with a concrete hosted consumer |
| Realtime | Low-frequency archive-complete/coverage/status notifications to authenticated research UI | Channel authorization and replay/reconnect behavior need separate proof. Realtime authorization does not persist broadcast messages in `realtime.messages`; authoritative state remains queryable. [Authorization](https://supabase.com/docs/guides/realtime/authorization), [Postgres Changes](https://supabase.com/docs/guides/realtime/postgres-changes) | Keep current local SSE for live forecasts; optional cold-status notifications |
| Hosted Pipelines | An asynchronous downstream warehouse copy of hosted structured history for larger research scans | Current public-alpha destinations: BigQuery, ClickHouse, DuckLake and Snowflake. Eligible paid plan does not guarantee access. Per-table source order and at-least-once delivery do not supply atomic cross-table archive visibility. [Current FAQ](https://supabase.com/docs/guides/database/replication/pipelines-faq) | Defer until measured research queries justify warehouse cost |
| Analytics Buckets / Iceberg | Possible bulk historical research datasets with external Iceberg clients | Creation guide marks private alpha and explicitly requires your own ingestion: Pipelines into Analytics Buckets is unsupported. Existing raw JSON/compressed chunks do not become analytical tables automatically. [Analytics setup](https://supabase.com/docs/guides/storage/analytics/creating-analytics-buckets) | Separate future experiment, no automatic raw-archive upgrade |
| pgvector | Optional semantic retrieval over rules/news/annotations or a measured historical similarity experiment | Vector search needs embeddings and evaluation; exact numerical history and official outcomes remain ordinary data. Filtered approximate search may return fewer matches. No paid embedding calls are authorized. [pgvector](https://supabase.com/docs/guides/database/extensions/pgvector) | Defer until a retrieval question beats SQL/FTS |
| Vector Buckets | Larger embedding corpus outside primary relational storage | Alpha capability with its own indexes, metadata and query contract. It stores vectors, not a substitute for complete exact event/revision archives. [Vector buckets](https://supabase.com/docs/guides/storage/vector/introduction) | No immediate archive efficiency benefit demonstrated |
| FDW / Wrappers / postgres_fdw | Read external research datasets from private hosted SQL | Federation queries remote data; it is not a durable backup. Wrappers lack RLS and belong in private schemas. Connecting back to VMs introduces network exposure and availability coupling. [Wrappers](https://supabase.com/docs/guides/database/extensions/wrappers/overview), [postgres_fdw](https://supabase.com/docs/guides/database/extensions/postgres_fdw) | Avoid exposing hot VM databases for convenience |

## S3 Wrapper as a future archive-scan option

The [S3 Wrapper guide](https://supabase.com/docs/guides/database/extensions/wrappers/s3) supports read-only CSV, JSONL and Parquet foreign tables, compression, Vault-held credentials and a Supabase Storage endpoint. It has no query pushdown or S3 Select, requires text columns for CSV/JSONL, and loads compressed files into memory. These costs matter on the observed small hosted compute instance. Our compressed canonical archive format also needs compatibility proof; an S3 endpoint alone does not make it a valid foreign table.

The browser audit found Wrappers disabled and a setup template including `GetObject`/`ListBucket`; current official guide instead lists `GetObject`/`GetObjectAttributes` and version-specific variants. Record that difference rather than assuming every wrapper needs listing. The existing PP reader denies listing and uses an authenticated HTTP identity. The wrapper's documented connection options do not establish support for that JWT session-token flow, while generated Supabase S3 credentials bypass Storage RLS. Do not broaden the archive reader or install a global key for this experiment. A future isolated, bounded derived export could be useful for research scans after permission, format, memory and cost qualification; no wrapper was installed or queried here.

## Pipelines freshness and operational costs

Direct official web pages were necessary: the Supabase documentation search tool returned an older private-alpha/BigQuery-only FAQ, while the current FAQ is dated November 16 and lists four public-alpha destinations. The prior cold-history prototype research repeats the older description; treat that paragraph as superseded by this report. Product documentation still does not prove availability in TokenBot.

The [current setup guide](https://supabase.com/docs/guides/database/replication/pipelines) places managed workers in Frankfurt (`eu-central-1`) and charges for pipeline hours, initial copying and ongoing replication, with destination charges separate. It installs database tracking objects and replication slots; stalled consumers retain WAL, and reset/recovery can rebuild destination data. This adds operating obligations rather than replacing exact local-outbox receipts. No pipeline or slot was created. No source-WAL, networking or cost experiment was run.

The [open-source ETL engine](https://github.com/supabase/etl) can run separately and lists the same four destination modules. That is independently operated infrastructure, not evidence that every hosted integration is activated for this project. No CDC throughput or cost savings are claimed.

## Sequencing and acceptance evidence

1. Implement the existing cold-reader contract locally and measure exact envelope payload reads with a dedicated identity after release-owned backfill is complete. Record rows/bytes, setup/query/verification latency and coverage; a receipt count alone is insufficient.
2. Compare the existing private SQL path with one bounded Data API/RPC candidate on equivalent reviewed IDs, preserving identical hash validation. Require wrong-origin and mutation-denial evidence, bounded resources, outage isolation and unchanged VM prediction freshness. Do not assume HTTP is faster.
3. Add low-frequency hosted coverage summaries or a Cron-triggered worker only when this removes measured polling/work. Derive archive state from durable records and retain reconciliation after notification loss.
4. Qualify independent raw-object backup/restore alongside relational recovery. Current direct backup docs say PITR is available on all compute sizes; older search snippets requiring Small are stale. Neither PITR nor same-project Storage alone proves raw-byte disaster recovery.
5. Consider a warehouse/analytics/vector layer only after a concrete research query, volume and acceptable cost are measured. Separate PP/prod role and provenance validation remains required even when they share one hosted project.

The [changelog](https://supabase.com/changelog.md) was inspected. CLI v3 remote targeting/confirmation changes and recent HTTP TLS cipher retirement matter for future tooling; this review installed nothing, weakened no TLS checks and changed no hosted state. This matrix is a reasoned application assessment from official documentation, not an exhaustive reading of every Supabase documentation page or a deployment approval.
