# Supabase followups after the deep dashboard review

Reviewed November 19, 2026. Scope: official-documentation/source assessment and local research documentation. No hosted SQL, grants, settings, integrations or credentials changed. The browser's [31 integration overview inventory](evidence/supabase-deep-navigation-2026-11-19.json) supplies availability observations; an overview is not an installed or qualified capability.

## Security Advisor: exposure is not demonstrated exploitability

The deeper browser pass reported zero Security Advisor errors, three warnings and eleven informational findings. Two warnings concern `public.rls_auto_enable` being `SECURITY DEFINER` with broad EXECUTE access; the third concerns disabled leaked-password protection. Those are useful review signals, not evidence that an attacker executed code or read private history. Supabase explicitly notes that advisor findings require interpretation against the intended access model. [Advisors](https://supabase.com/docs/guides/observability/advisors)

A separate read-only SQL metadata snapshot at **07:41:19.646145 UTC** confirmed this exact function uses `plpgsql`, returns `event_trigger`, is `SECURITY DEFINER`, and grants effective EXECUTE to `anon` and `authenticated`. An explicit `search_path=` configuration entry exists; its value and the function body were not retrieved, so a safe path/body is not established. PostgreSQL event-trigger functions need special invocation context. For this PL/pgSQL return type, an ordinary SQL/RPC call is rejected before its body executes: PostgreSQL 17's normal-function compiler rejects `EVENT_TRIGGEROID` with “trigger functions can only be called as triggers.” This is a source-based conclusion, not an invocation of the live function. Full body, owner, search-path value, dependencies and overloads remain unreviewed. An EXECUTE grant and an exposed-schema count alone do not prove a working ordinary RPC or an RLS bypass. [PL/pgSQL trigger documentation](https://www.postgresql.org/docs/17/plpgsql-trigger.html), [PostgreSQL 17 compiler source](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/pl/plpgsql/src/pl_comp.c#L512)

Do not instead claim that PostgREST always hides event-trigger functions: its v12.2.12 schema-cache query explicitly excludes `trigger`, without the same exclusion for `event_trigger`. The deployed PostgREST version and actual endpoint/cache behavior were not tested here. Ordinary-call visibility and successful event-trigger execution are different questions. [PostgREST schema-cache source](https://github.com/PostgREST/postgrest/blob/v12.2.12/src/PostgREST/SchemaCache.hs#L435)

Revoking unnecessary client EXECUTE grants is a plausible hardening followup. In core PostgreSQL 17, existing event triggers are invoked by stored function OID with `EventTriggerData`; that firing path does not recheck the ordinary caller's EXECUTE ACL. **Inference:** revoking broad client EXECUTE should preserve an existing automatic-RLS event trigger. This is not a managed-Supabase compatibility test. Do not disable/drop `ensure_rls`, change its security mode or blindly replace its body to clear a warning. First reproduce the revoke plus subsequent table-creation/RLS behavior in a disposable compatible fixture and review managed extension behavior; release ownership and freeze still apply. [Event-trigger invocation source](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/backend/commands/event_trigger.c#L1007), [Supabase automatic-RLS example](https://supabase.com/docs/guides/database/postgres/event-triggers)

Disabled leaked-password protection is an Auth hardening gap, not proof that machine passwords leaked or that archive integrity failed. Supabase's protection checks known compromised passwords and is available on Pro and above. It does not replace strong generated machine credentials or rotation qualification. Review subscription eligibility and machine sign-in/renewal compatibility separately; no setting was enabled here. [Password security](https://supabase.com/docs/guides/auth/password-security)

Prioritize accurate function classification and dependency review before any production security mutation. Preserve the automatic RLS safety net. No error finding does not mean no risk; warning counts do not measure exploitability.

## Three useful next uses without another storage platform

1. **Use existing observability to measure the archive bottleneck.** The current browser inventory labels Grafana installed, a change from the earlier two-integration audit; this review neither activated it nor identified who did. Inspect its existing dashboard and scrape health before adding anything. Correlate hosted memory/WAL/connections with VM outbox age, acknowledged rows per second, connection setup, revision-byte readback and raw PUT/GET times, keeping PP/prod labels separate. The Metrics API supplies hosted PostgreSQL metrics, not VM application metrics automatically. Start with an offline dashboard/query specification and existing sanitized evidence; keep privileged scrape credentials server-side. This can distinguish network setup from memory pressure and prevent an unsupported compute upgrade claim. No paid feature activation is needed to design or inspect existing telemetry. [Metrics API](https://supabase.com/docs/guides/observability/metrics), [Grafana integration](https://supabase.com/docs/guides/observability/metrics/grafana-cloud)

2. **Make an independent read-only recovery verifier.** Extend the existing exact raw GET/manifest/receipt checks into a bounded operator report for selected retained generations: expected versus recovered IDs, original bytes/hashes, missing objects/revisions, original timestamps and exact decimals. Distinguish structured-revision coverage from raw-event coverage and never mint retirement authority. First use generated fixtures and retained test artifacts; the release owner chooses any real PP/prod scope and credentials. An independent object copy and isolated restore remain separate future evidence: same-project successful GET is not disaster recovery. This closes a more immediate gap than creating an Analytics Bucket. [Database backup limits](https://supabase.com/docs/guides/platform/backups), [Private Storage access](https://supabase.com/docs/guides/storage/buckets/fundamentals)

3. **Profile existing SQL before adding indexes, RPCs or warehouses.** `pg_stat_statements` is already observed enabled. Design bounded before/after snapshots for the exact historical receipt/revision SELECTs, plus nonexecuting EXPLAIN on a disposable representative dataset. Combine server execution/rows with application round trips, wire bytes and connection timing; do not treat cumulative legacy upsert means or low-volume unused-index findings as the current cold-reader bottleneck. A candidate server-side summary/RPC or index should follow measured benefit, then exact-decimal and role-isolation tests. Existing Supabase SQL and the current transport are enough to gather the baseline; no Data API grants, replication slots, new extension or paid destination is needed for this step. [Query optimization](https://supabase.com/docs/guides/database/query-optimization), [pg_stat_statements](https://supabase.com/docs/guides/database/extensions/pg_stat_statements)

The remaining catalog entries mostly expose unrelated payment, CRM, scheduling and identity datasets. Keep them as researched options rather than new runtime dependencies. Cron/Queues/Webhooks can later schedule or notify durable secondary work; S3/Iceberg/warehouse wrappers can later serve a measured research export. Neither creates archive coverage or reduces hot-path latency just by being installed. The platform's live prediction path remains VM-local throughout these followups.
